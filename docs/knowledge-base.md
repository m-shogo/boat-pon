## 4. 手法の罠

1. ROI は公式払戻で出す。表示オッズ（current_odds）・T-5 オッズの EV は楽観的（K4）。
2. in-sample → 外部検証 → held-out → forward の順を飛ばさない。同じ外部データで何度も検定しない。
3. 判定の条件（閾値・会場・時間帯）を細かく分けるほど、見かけの ROI は上がる。分けた数だけ、偶然の当たりを拾う。
4. 信号は「行動できた時点」で評価する。締切後に付いたラベルや、後から届いた情報で作った判定は、成績に入れない（K5）。
5. 精度は「同じレース」で比べる。期間ごとの logloss の値そのものは、含まれるレースで上下する（成長レポートは差で比べる）。
6. 分布と価格を分けて見る。「よく当たる」と「儲かる」は別の問い（K3・R5）。
7. 帯や条件を「結果で決まる値」（当たった買い目の払戻など）で分けない。結果で選んだ帯は、ずれが無くてもずれて見える（2連複 ÷ 2連単2点を2連単の払戻で分けると 1.715〜0.735。着順に左右されない2連複の払戻で分けると 0.92〜1.10。K11）。

## 5. 運用の教訓

1. **決定的な実験を先に回す。** 2026-07-26 には判定に必要なサンプルがそろっていたのに、8〜9月の研究基盤のコミットは 2,124件（成長レポートの集計）で、判定は 10/7 まで回らなかった。基盤の作業は「次の決定的実験に必要か」で選ぶ。
2. **「success」は中身で見る。** 取得件数・精算件数・最終日付で監視する。終了コードだけを見ない（private capture は認可切れで 0件のまま success を出し続けた）。
3. **一度きりのバックフィルは、毎日の取り込みにも入れる。** 全券種の払戻は 6/5 に一度入れたきりで、122日空いた。
4. **記録は行動の締め切りで固定する。** 締切後の再評価で上書きしない（2026-10-09〜）。判定の時刻は「判定の段階の時刻」を使う（実行開始時刻を使って 26行がすり抜けた。2026-10-14 に修正）。

7. **毎回「全期間」を読む処理は、データが増えるほど遅くなる。** auto-odds は判定の前に全期間のオッズ（約230万行）を毎回読み、約40秒かかっていた。遅さは少しずつ増えるので気づきにくい。ライブ経路は、その日のデータだけを読む（2026-10-14 に修正。判定は 12 通りの比較で一致）。
8. **外部サービスの上限は、止まる前に数える。** LINE の無料枠は月 200 通（2026-10-15 に API で確認。8月は 187 通でぎりぎりだった）。超えると月末まで通知が止まり、その知らせも LINE では届かない。21:30 のはずれは日次まとめに載せて1通を減らし、毎晩のスコアカードが使用量を見る。
9. **取り直せないデータは、別にして毎日残す。** DB 全体のバックアップは 2026-06-11 で止まり、同じディスクにしか無かった。締切前のオッズの時系列（取り直せない）は、2026-10-15 から毎晩1日1ファイル（数百 KB）で書き出している。
10. **同時に動くジョブは、送る前に押さえる。** 21:30 は2つのジョブが同じ通知の記録を読むので、「読んで、送って、送信済みにする」だと二重に送りうる。送る前に状態を条件にして押さえ（SENDING）、書く側でも状態を条件にする（2026-10-15、Codex のレビューで再現して直した）。
11. **別のモデルにレビューさせる。** 2026-10-15 は Codex（読み取り専用）に6回レビューさせ、12 件（P1 ×3）を見つけて直した。自分で書いたコードの穴（並行処理・失敗時の経路・形式の取りこぼし）は、自分では見落としやすい。
12. **知識の量は「教訓の数」で測れる。** lessons-learned の項目は 5月 23件 → 6〜9月 0件 → 10月 3件。8〜9月はコミットが最も多かったが、人が読める知識は増えていなかった（研究工場の学びは `research/registries/learnings/` の機械向け JSON 11件だけ。このフォルダは 2026-10-15 に main から外した）。
