# 設定変更ゲート

Boat Pon の設定変更は、分析、検証、live反映を別工程として扱う。
特に `app_settings`、`decision_history` 再生成、外部取得、バックフィルは同じ勢いで連続実行しない。

## 基本方針

- live設定は、外部検証が終わるまで反映しない。
- ROIが良い条件を見つけても、探索期間と検証期間を分ける。
- フィルターは足し算しすぎない。3条件以上の組み合わせは過学習候補として扱う。
- `data/boat.sqlite` を分析するだけの作業では、原則 `mode=ro` で開く。
- `data/raw/official` と既存取得プロセスは、明示目的なしに触らない。

## live反映前チェック

1. 現在時刻を `date` で確認した。
2. `git status --short` で未コミット差分を確認した。
3. 変更前の `app_settings` を保存した。
4. 変更するキーと値を1つずつ列挙した。
5. 戻し手順を先に書いた。
6. 探索期間、検証期間、除外期間を明記した。
7. 月別、会場別、レース番号別、時間帯別の崩れを見た。
8. 直近期間だけでなく、モデルバージョン差と欠落期間を確認した。
9. BUY数、的中数、ROI、calibration、0的中月数を確認した。
10. live反映の可否をユーザーに確認した。

## バックフィル前チェック

1. 対象期間と対象条件を明記した。
2. `SELECT COUNT(*)` で対象件数を出した。
3. `--dry-run` で対象とログを確認した。
4. 1件または小さい `--limit` で実行時間を測った。
5. 総所要時間、sleep間隔、停止条件を見積もった。
6. キャッシュ方針と外部アクセス頻度を確認した。
7. 実取得が必要な理由と対象範囲を説明した。

## やってはいけない順序

- 外部検証前に `app_settings` の live値を反映する。
- 件数と所要時間を出さずにバックフィルを開始する。
- SQL後処理のROIだけを根拠に、本番ルールを採用する。
- `--refresh-existing` の結果を完全再生成と同等に扱う。
- 旧モデルと新モデルの履歴を混ぜたまま設定効果を判断する。
- オッズ履歴が1スナップ中心なのに、時系列オッズ戦略を検証済み扱いにする。
- 分析スクリプトの変更とlive設定変更を同じ作業単位で実施する。

## 推奨順序

1. 仮説を書く。
2. 読み取り専用SQLで粗く見る。
3. 探索期間と検証期間を分けて再現する。
4. `DELETE + 再生成` が必要な評価か確認する。
5. 月別、会場別、レース番号別、時間帯別、直近期間で見る。
6. 外部検証が必要なら、対象範囲と取得頻度を先に決める。
7. dry-run または小さい範囲で実行する。
8. 変更前後と戻し手順を記録する。
9. ユーザー確認後にlive反映する。
