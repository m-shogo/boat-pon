# 何年先も壊れないために・プロの考え方の取り入れ方（2026-10-16）

ユーザーの依頼（10/16）: DB も含めて今後破綻しないようにしたい。ベンター式や、知らないプロの考え方も、良いところだけボートレースに取り入れたい。

## 1. DB と仕組みが何年先も壊れないか（実測 2026-10-16 01:00〜01:45）

| 見たこと | 数字 | 判断 |
|---|---|---|
| DB の大きさ | 16.6 GB（いちばん大きいのは締切前のオッズの時系列 5.3 GB と、その索引 3.6 GB） | — |
| 増え方 | オッズの時系列は 8月以降 月 約150万行（6〜7月は研究工場のころで月 1,650万〜3,300万行）。締切前のオッズ全体で月 約0.5 GB、年 約6 GB | 10年で約 +60 GB |
| ディスクの空き | 269 GB（スコアカードが 20 GB を切ったら注意） | 容量で止まるのは何十年も先 |
| 壊れていないか | `PRAGMA quick_check` = ok（読み取り専用で 248 秒） | いまは健全 |
| 書き込みの方式 | WAL・synchronous NORMAL・ロック待ち 30 秒 | スリープや電源断に強い設定 |
| 取り直せないもの | オッズの時系列と、判定・通知・設定の記録を毎晩書き出し、Google Drive に複製（10/15〜） | ディスクが壊れても残る |
| 取り直せるもの | 番組・結果・払戻は公式の K・B ファイルから取り直せる | DB 全体のバックアップは必須ではない |
| Node | `.nvmrc` で 24 に固定、CI も同じ。DB は Node の `node:sqlite`（まだ実験的な扱い） | Node のメジャーを上げるときだけ注意 |

### 今回足したもの

- **月1回の点検**（`scripts/monthly-db-check.ts`、毎晩の daily-notify の最後で、前回から 28 日たつと動く。約5分）:
  1. `PRAGMA quick_check`（壊れていないか）
  2. **復旧の練習**: 書き出し（判定・通知・設定と、直近7日のオッズの時系列）を、一時ファイルの新しい DB に実際に戻し、行数が書き出しと本番の DB に合うかを確かめる。戻せないバックアップは、無いのと同じ。本番の行が前の晩の書き出しより減っていたら、それも問題にする
  3. 複製先（Google Drive）に同じ書き出しがあるか
  結果は `data/reports/scorecard/db-check.json`。問題があるか、40日以上点検していなければ、日次まとめの「⚠️ 注意」に出る。

### 壊れ方ごとの備え

| 起きること | 備え | 戻し方 |
|---|---|---|
| ディスクの故障・PC の買い替え | 取り直せないものは毎晩 Drive に複製。月1回、戻せることを練習で確かめる | 新しい PC で repo を clone → K・B ファイルを取り直す（夜間に数日）→ 書き出しを戻す |
| DB が壊れる | WAL・月1回の quick_check | 壊れた DB は消さずに残し、新しい DB に取り直しと書き出しで作る |
| 遅くなる | 判定は当日分だけ読む。読み込み 20 秒・判定の遅れで注意 | 注意が出たら、全期間を読む処理を探す（A4 の残り） |
| 公式サイトの形が変わる | データの鮮度の注意（結果・番組・オッズが止まったら出る） | 取得のパーサーを直す |
| LINE の枠・仕様 | 使用量と送信失敗の注意 | 送る量を減らす（はずれは日次まとめにまとめる） |
| Node・依存の更新 | `.nvmrc` と lockfile で固定。`npm run verify` と `npm run health` を通してから上げる | 戻すときは lockfile を戻す |
| 何年も経って DB が大きすぎる（目安 100 GB） | 年ごとの書き出しはもうある（1日1ファイル） | 古い年を別の DB ファイルに移す。行を消すのでユーザーの承認が要る |

## 2. プロの考え方: 取り入れるもの・取り入れないもの

| 考え方 | 出どころ | 取り入れ方 | 状態 |
|---|---|---|---|
| **市場と戦わず、市場と混ぜる**（2段目で自分の予想と市場の確率を混ぜる） | ベンター（1994） | 市場補正の確率が土台。基礎モデルを混ぜる検証をした（K12: 市場をわずかに上回る・保留） | 取り入れた |
| **物差しは「市場に足して増えた分」（ΔR²）** | ベンター | 新しい考えはすべて、まずこの物差しで測る。回収率は数千ベット要るが、これなら数千レースで決まる | 取り入れた（10/16 の検証で使った） |
| 先に合否を決める・未使用の期間で確かめる | 統計・投資の研究の作法 | 事前登録・forward（もう使っている） | 取り入れた |
| その時点で手に入った値だけを使う | 同上（「先読み」を防ぐ） | 10/16 の検証で、展示を「締切5分前までに取れたものだけ」で数え直した（0.0031 → 0.0021） | 取り入れた |
| 有利さを割り引いて、資金の一部だけ賭ける（分数ケリー） | ベンター・ケリー | 有利さが確かめられるまでは実際のお金は 0。確かめられたら、見積もりを割り引いて 1/4〜1/2 ケリーから | 方針として記録 |
| 確定時の値段を見積もる | ベンター（「確定時のオッズの見積もりが要」） | 締切5分前のオッズで計算した期待値は 5〜8% 楽観的（K4）。期待値には T-5 × 0.95 を使う | 取り入れた（CLAUDE.md） |
| 値段が自分の側に動くか（クロージング・ライン） | スポーツベッティングのプロ | BUY の後、締切5分前 → 確定でオッズが下がる（人気が集まる）割合を見る。回収率より少ない件数で「市場が同じ考えか」がわかる | 提案（3連単の確定オッズを全部は持っていないので、まず T-10 → T-5 で） |
| 連敗の見込みを知っておく | 資金管理の基本 | 的中率 1.6% なら、40 回続けて外れることは珍しくない（約 52%）。財布の下がり方を「運か、見込み違いか」で読む | 提案（日次まとめの財布に1行） |
| 情報で勝つ（モデルの種類より、市場が持っていない材料） | ベンター・現代の機械学習の実務 | 効いていたのは展示タイム（K12）。次の材料の候補は各場のオリジナル展示（一周・まわり足・直線）。新しい種類の取得なので承認が要る | 候補 |

取り入れないもの:

- **候補を自動で量産する仕組み（研究工場）**: 6〜9月に作って、補強ばかりで判定が進まなかった。候補を増やすほど偶然の当たりが増える。
- **負けを取り返す賭け方（マーチンゲールなど）**: 破産の確率が上がるだけ。
- **予想屋・ネットの予想の寄せ集め**: ベンターの検証で、新聞の予想を市場に混ぜても +0.0002（意味なし）。
- **フルケリー**: 有利さを2倍に見積もり違えると、資金が減っていく（ベンター）。
- **条件を細かく分けて見かけの回収率を上げる**（手法の罠3）。
- **海外の割り戻し・取引所**: 海外のプロの利益の多くは割り戻しと量から来ている。日本の競艇には無い（K10）。
- **重いモデル（深層学習など）を先に作ること**: 材料に市場が持っていない情報が無ければ、モデルを複雑にしても市場は越えられない。
