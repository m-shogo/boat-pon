## 結論

1. **利益が出る優位性（edge）は無い。** 7月に事前登録した決定的検証を forward 9,417 レース（必要数 1,000 の 9.4 倍）で再実行し、全月で不合格だった。最後に残った有力仮説（締切直前の資金の動き）も、結果を見る前に基準を固定して検証し、不合格だった。paper-live の BUY は実払戻 ROI 63.4%（175件中3的中）。7月の[利益可能性監査](../profit-feasibility-audit.md)が自分で決めていた撤退条件（6項）を満たした。
2. **8/15〜9/24 の 1,656 コミットは、この判定に何も寄与していない。** 約96%（1,587件）が `fix(research)` で、件名に publication・descriptor・identity・ledger などの補強系の語を含むものだけでも 822件ある。決定的実験は、forward のサンプルが 1,000件を超えた **7/26 から実行できた**のに、一度も再実行されていない。
3. **その間、唯一大事なデータ収集が止まっていたり不安定だったりした。** private capture は 9/6 に認可が期限切れになり、それから32日間 1件も取れていない。auto-odds は、ノートPCのスリープと fetch にタイムアウトが無いことが原因で、日によってカバー率が 10〜40% まで落ちていた。
4. **同じ結論は 2026-06-05 にも出ていた。** ただし Claude の private memory にしか書かれておらず、repo の docs には無かった。6月に「最後の未踏」として残した sharp money も、今回の late money 検証で閉じた（下の「補足」を参照）。

## 数字

### 1. 事前登録の T-5 市場残差検証の延長（6月だけで学習してパラメータを固定し、7/1〜10/7 で forward）

| モデル | forward logloss | Brier | 1位1点 ROI（公式払戻） | 上位2件除外 |
|---|---:|---:|---:|---:|
| T-5 市場 | 3.8014 | 0.9596 | 69.28% | 68.70% |
| 市場 temperature T=0.9 | 3.7907 | 0.9594 | 69.28% | 68.70% |
| 買い目残差（事前登録） | **4.0054（悪化）** | 0.9688 | 73.85% | 73.07% |
| 買い目残差（月次 walk-forward 再学習） | 3.8400（悪化） | – | 76.07% | 75.37% |

- 月別 logloss 差（残差 − 市場）: 7月 +0.229 / 8月 +0.199 / 9月 +0.204 / 10月 +0.166。**全月で市場に負けている。**
- EV ベット（モデル確率 × T-5 オッズ ≥ 閾値、公式払戻で精算）: 閾値を 1.0〜1.5、オッズ上限を ≤100 にしても ROI は 55〜77%。
- 全120通りを均等に買った場合の ROI は 59.4%。
- 本命・大穴の偏り（favourite-longshot bias）は明確にある。オッズ 1〜10倍では実際の的中が市場確率の 1.09倍あるが、それでも ROI は 75.2%。300倍以上は 0.54倍で、ROI 45.7%。
- **T-5 → 確定払戻のドリフト**: 的中した買い目の確定払戻は、T-5 オッズの平均 95.2%（中央値 92.2%）。締切直前に入る資金の方が情報を持っている。T-5 オッズで計算した EV は、最初から 5〜8% 楽観的になる。

### 2. Late money 仮説（2026-10-07 に結果を見る前に事前登録 → 不合格）

- 定義: T-10（無ければ T-20）から T-5 までの市場確率の変化を補正項に入れる。7〜8月で学習し、9/1〜10/7 を forward（3,604 レース）。
- forward logloss は 3.7682 で、市場の 3.7838 を **わずかに上回った（情報は実在する）**。モメンタムの十分位で見ると、実際の的中と期待値の比が 0.47 → 1.13 と単調に増える。
- それでも EV ベットは 136件で ROI 51.9%（上位2件除外では 25.4%）。一番強い十分位を均等買いしても ROI は 59%。
- **判定: REJECT。** 情報はあるが、控除率 25% と直前のドリフトを越える大きさにはまったく届かない。

### 必要な改善幅

最も有利なオッズ帯（1〜10倍）でも、確定払戻ベースの ROI は約75%。損益分岐に届くには、選んだ買い目で市場より **約1.33倍** よく当てる必要がある。実際に観測できた中で最も強い構造的シグナル（late money 上位十分位）でも 1.13倍。公開情報だけを使うモデルで、払戻の上乗せ（リベート）も無い条件でこの差を埋められる根拠は、どのデータにも出ていない。

## 進め方の問題（厳しめに）

1. **目的がすり替わっている。** 守るべきだったのは「edge があるかを最小コストで判定すること」だった。実際には「研究基盤の完全性」が目的になっていた。
   - 1,656コミット中 1,587件が `fix(research)`。件名に harden/bind/descriptor/identity/ledger などを含むものが 822件。
   - テストコード 102,546行に対して本体は 68,765行。`src/research-replay` は 925 ファイルで、`*Boundary.test.ts` だけで 258。npm scripts は 261。docs は 140 ファイル。
   - 象徴的な例が `scripts/analyze-t5-residual-forward.ts`。86行のうち約40行が「レポートを原子的に publish する儀式」で、分析本体は数行しかない。
2. **一番価値のある行動を飛ばした。** 決定的実験はスクリプト1本で2分で終わる。7/26 から実行できたのに、2.5ヶ月間だれも回さなかった。コミット件名の中に、新しい edge の判定を出したものは見当たらない。
3. **「success」が正常の証拠になっていなかった。** N2 rollup は1日3回「success」と出していたが、capture は認可切れで 0件だった。週次レビューは毎週「settledBUY: 0」と出していた。どちらも中身を見れば異常だと分かる。
4. **期限付き認可が時限爆弾になっていた。** 30日で切れる認可（`expiresAt 2026-09-06`）に、更新を促す通知が無かった。しかも capture は `maxRequestsPerDay: 48` の設計で、1日 150〜180 レースに対して最大でも約3割しか取れない。auto-odds とも重複している。
5. **本番インフラがノートPCだった。**
   - バッテリー駆動で蓋を閉じると Clamshell Sleep に入る（`caffeinate -s` は AC 電源のときしか効かない）。
   - `fetch` にタイムアウトが無く、直近2,000回の実行のうち 30回が30分を超えた（最大 2.7時間）。その間 launchd は次の実行を起動しないので、T-5 の窓を丸ごと逃す。
   - launchd はこの作業コピーを直接実行しているので、`git pull` がそのまま本番のコード更新になる。
6. **public リポジトリに self-hosted runner を置いている。** 今のワークフローは `ref: main` を checkout しているので、fork からのコード実行は防がれている。ただ構造としては脆い（具体的な指摘はオーナーに直接伝え、ここには書かない）。GitHub の公式ガイダンスでも、public リポジトリでの self-hosted runner は非推奨。
7. **指示文とメモが古くなっている。**
   - `CLAUDE.md` の「現在フェーズ（2025-06 時点）」は年が誤っていて、中身も6月の状態のまま。コマンドは `pnpm` と書かれているが、CI は `npm ci`（`pnpm-lock.yaml` の最終更新は 2026-06-02）。
   - エージェント用 memory に「payout_yen はダミー、current_odds で ROI を出す」という廃止済みの指示が残っていた（今回修正済み）。
8. **Git の衛生状態が悪い。**
   - リモートブランチが 2,442本。内訳は PR マージ済み 2,185 / PR なし 168 / 未マージで close 86 / open 1。
   - `delete_branch_on_merge` が無効。
   - GitHub に登録されたワークフローが 130件あり、うち 117件は main に定義ファイルが無い残骸。
   - stash に自動生成物が2件たまっていた。
   - 0バイトの `boat.sqlite` が追跡対象になっている。
   - 週次ジョブが追跡対象の `docs/rule-candidates.md` に追記するので、作業ツリーが毎週汚れる。

## 補足: 同じ結論は 2026-06-05 に一度出ていた（repo には書かれていなかった）

Claude の作業メモ（エージェント用 memory）には、2026-06-05 の時点で次の結論が残っていた。repo の docs には書かれておらず、別のエージェント（ChatGPT の control plane など）からは見えなかった。**以下は当時の記録の転記で、今回は再検証していない。**

- 推定的中率の十分位で見ると、モデルは的中率を識別できている（実際の的中率 5% → 9.7% と単調に上がる）。それでも ROI は全十分位で 0.75〜0.86 とフラット。的中率が上がる分だけオッズが下がって相殺され、モデルは市場と同じ情報しか持っていない。
- 人気順・フォーメーション・展示・会場・天候・チルトなど、公開情報の単軸はすべて ROI 0.57〜0.86。
- 2004〜2025年の約109万レースで、全券種の1番人気 ROI は 0.76〜0.78。券種を変えても余地は無い。
- 強風の信号は23年で再現する本物だが、どの人気帯でも ROI は 1 未満。
- 当時の結論:「公開情報では利益化不可能と確定。残る唯一の未踏はオッズ時系列（sharp money）」。

今回 REJECT した late money の検証は、この「最後の未踏」そのもの。**6月に残した最後の候補も、これで閉じた。**

進め方の問題として: 決定的な結論が、1つのエージェントの private memory にしか無かった。判断に効く結論は、必ず repo の docs（このプロジェクトなら `docs/profit-feasibility-audit.md`）に書く。

### 停止の手順（ユーザーが実行する）

方針 B では、止めるのは研究工場の部分だけ（認可切れの private capture・意味を失った wind24 監視の週次通知・バグのある週次レビュー・self-hosted runner）。収集と通知は止めない。plist は消さない。`disable` は再ログイン後も有効で、`enable` + `bootstrap` で元に戻せる。方針 A（全部止める）にする場合は、このリストに収集・通知のジョブも加える。

```bash
for L in com.boatpon.trifecta-private-capture com.boatpon.weekly-forward-notify com.shogo.boat-pon.weekly-review actions.runner.m-shogo-boat-pon.boat-pon-mac-local; do launchctl disable gui/$(id -u)/$L; launchctl bootout gui/$(id -u)/$L; done
```

収集ジョブが動いていない時間帯（21:05〜翌8:00 JST）に実行する。再開するときは、ジョブごとに `launchctl enable gui/$(id -u)/<label>` を実行してから `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist` を実行する。

runner の登録解除は GitHub の Settings → Actions → Runners から行う（`boat-pon-mac-local`）。

GitHub Actions の CI 以外のワークフローを無効化する（再開は `.../enable`）:

```bash
gh api --paginate 'repos/m-shogo/boat-pon/actions/workflows?per_page=100' --jq '.workflows[] | select(.path != ".github/workflows/ci.yml" and .state == "active") | .id' | while read id; do gh api -X PUT "repos/m-shogo/boat-pon/actions/workflows/$id/disable"; done
```

## 2026-10-08 追記3: BUY の 82% は締切後に付いたラベルだった

### 事実（読み取り専用の集計）

paper-live BUY 178件を、締切前にリアルタイム通知できたかどうかで分けた。

| 区分 | BUY | 的中 | 実払戻 ROI |
|---|---:|---:|---:|
| 締切前に通知できた | 32 | 0 | 0% |
| 直前情報が締切後に届き、締切後に BUY 判定 | 94 | 1 | 31% |
| 締切前に情報はあったが通知なし | 52 | 2 | 160% |

- **実際に行動できたタイミングで見ると、32件で0的中。** これまでの「BUY 175件・ROI 63.4%」は、締切後に付いたラベルを含んだ数字だった（edge なしという結論は変わらない。むしろ強まる）。
- リアルタイム通知は 10/2 を最後に止まっていた。10/3〜10/7 の BUY は、どれも夜 21:30 の日次処理でしか届いていない。

### 原因（コードとデータで確認）

1. **直前情報の到着が遅い。** `requireBeforeInfoForBuy` が true なので、直前情報がそろうまで BUY にならない。直前情報の取得（auto-exhibition）は30分おきで、締切60分前から「データが入るまで1レース1回」試す。展示の前に空振りすると次は30分後で、締切を過ぎている（例: 10/4 津4R は締切の86分後、10/6 常滑8R は16分後に到着）。
2. **締切後も判定が上書きされる。** auto-odds は、オッズのある当日の候補を毎回再評価して `decision_history` を上書きする（夜まで続く）。
3. **締切を過ぎると「締切が近すぎる」が効かない。** `src/domain/decision.ts` の `minutesUntil` は、締切時刻を過ぎると翌日の同じ時刻までの分数（約1,400分）を返す。そのため締切後の再評価では、締切の条件をすり抜けて BUY になる。
4. 通知の条件で落とされた BUY はログに何も残らないので、5日間だれも気づかなかった。

### 今回直したこと（判定ロジックは変えていない）

- スコアカード: 通知のタイミング別の台帳。締切前に通知できた割合が 50% 未満なら警告する。
- LINE: 日次まとめに「うち締切前に通知できた BUY」の成績を足した。夜の BUY 通知は、締切後なら「🕘 締切後に BUY 判定（通知は間に合わず）」と見出しで明記する。確定結果と速報にも、締切前に通知できなかったことを書く。

### 承認がほしい修正（本番の判定・記録・launchd に関わるので、こちらからは入れない）

| # | 修正 | 効果 | 種類 |
|---|---|---|---|
| a | auto-exhibition の間隔を 30分 → 5分にする（plist の StartInterval 1800 → 300） | 直前情報が締切前に届くようになり、BUY が締切前に確定して通知される。公式サイトへのアクセスは1日数百回増える（1レースあたり、データが入るまで数回） | launchd（ユーザー作業） |
| b | `minutesUntil` が締切後に翌日へ繰り越さないようにする（締切後は負の分数を返し、「締切が近すぎる」で BUY にならない） | 締切後に BUY のラベルが付かなくなる。以後の paper-live 記録が「行動できた BUY」だけになる | 本番の判定ロジック（CLAUDE.md で変更禁止。承認が必要） |
| c | 締切後は `decision_history` を上書きしない（締切前の最後の判定で固定する） | 記録が「締切前に何と判定したか」を正しく残す | 本番の記録処理（承認が必要） |

b と c を入れても、過去の記録は書き換えない。過去分の区別は、今回のスコアカードが通知の時刻から出す。

## 2026-10-09 追記4: 根本修正と、成長ループの拡張

ユーザーから「上限までより良く」と指示があったので、追記3で承認待ちにしていた修正を、判定ロジックに触れない形で入れた。

### 記録を正しくする（課題 #19 の根本修正）

- **行動の締め切りで判定を固定する。** 締切の5分前を過ぎたレースは、auto-odds が判定し直さない。記録はその時点の判定で残る。これで、締切後に BUY のラベルが付くことも、BUY だった判定が締切直前に上書きされることも無くなる（追記3の原因 2・3 は、判定ロジックの `minutesUntil` を変えずに、ライブのループ側で塞いだ）。
- **1日の BUY 上限は、固定済みの BUY で数える。** これまでは締切後の「幻の BUY」が上限の5件を食い、締切前のレースが「1日最大BUY数に到達」ではじかれていた（追記3の区分「締切前に情報はあったが通知なし」52件の主な原因と考えられる）。
- **直前情報を締切前に取りに行く。** 締切 5〜25 分前で直前情報が無いレースは、auto-odds がその場で取得する（1回最大6件）。30分おきの auto-exhibition の設定（plist）は変えなくてよくなった（追記3の a は不要）。
